# 三进程 → 两进程：把 Wake 并入 Agent

日期：2026-10-20　状态：已实现

## 背景

原先有三个可执行文件：

| 产物 | 角色 | 寿命 |
|---|---|---|
| `tl.exe` | Wake：探测核心 → 按注册层拉起 → 启动助手 → 退出 | 秒级 |
| `tl-core.exe` | 核心：SSH 会话、端口转发、控制 API | 常驻 |
| `tl-agent.exe` | 助手：托盘 + 面板 | 随会话 |

Wake 存在的唯一理由是"用户双击的那个东西不该是常驻进程"。但它本身**没有任何独占资源**，
全部工作就是"读一下控制契约、必要时起个进程"，属于可以内联的编排逻辑。
多一个二进制带来的成本是实打实的：用户要知道双击哪个、打包多一份、文档多一节。

## 决策

把 Wake 合并进 Agent，三进程变两进程。

**保留 Wake 的代码，但只作为库**（`crates/tl-wake`，不再产出二进制）：
`tl_wake::ensure_core(data_dir)` 保留完整的探测与分流逻辑，由助手在两个时机调用：

1. 助手启动时（后台线程，不阻塞窗口出现）——双击助手即启动服务
2. 前端「启动服务」按钮（Tauri 命令 `start_core`）

## 为什么不合并另外两个方向

| 方向 | 结果 |
|---|---|
| Agent 并入 Core | Core 变 GUI 进程：SYSTEM 自启会话起不了界面；界面崩溃会带走所有转发 |
| Core 并入 Agent | 转发挂在带界面的进程里，UI 异常即断线；"零登录会话仍要服务"直接消失 |

保留 "无头核心 + 有界面客户端" 的边界是这套设计里最有价值的一条，不能为了让进程数变少而牺牲它。

## 影响与验证

- 自启路径**完全不变**：任务计划仍是直接执行 `tl-core --boot`，不经过任何前端。
- 打包：`externalBin` 只留 `binaries/tl-core`；`bundle-sidecars.ps1` 不再暂存 `tl.exe`。
- 脚本：删除 `smoke-wake.ps1`；`audit-lifecycle.ps1` 改为直接起核心并断言契约与 healthz。
- 验证：核心未运行时只启动助手 → 8 秒内 `tl-core.exe` 出现、`agent.log` 记录
  `startup: core ensured` / `core alive -> true`；生命周期巡检 7 项全绿。
