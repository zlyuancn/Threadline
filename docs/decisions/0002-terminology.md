# 0002 · 界面术语：端口转发 / 隧道 / 凭据

- 日期：2026-10-20
- 状态：**已生效**（界面与文档用词）

## 决定

界面上三层概念固定为：

| 界面用词 | 含义 | 内部标识符（不改） |
|---|---|---|
| **凭据** | 密码 / 私钥 + 口令 | `credential`、`/credentials` |
| **隧道** | 一条到远端的 SSH 连接（主机、端口、登录用户） | `server`、`/servers`、`ServersFile` |
| **端口转发** | 一条 `-L` 规则（本机端口 → 隧道另一端端口） | `tunnel`、`/tunnels`、`TunnelsFile` |

关系：`凭据 1 ─ N 隧道 1 ─ N 端口转发`。

## 为什么内部名不改

`server` / `tunnel` 已经贯穿：磁盘文件名（`servers.json` / `tunnels.json`）、HTTP 路径（`/servers`、`/tunnels`）、
DTO 名（`ServerDto` / `TunnelDto`）、机检规则里的路径、已有测试。全部重命名只会带来破坏性改动与新的不一致，
**没有任何功能收益**。因此只在「用户看得见的地方」（界面文案、README、错误提示）使用新术语，
并在代码里保留一句映射注释。

## 代价（诚实记录）

- 读代码的人会看到「UI 的隧道 = 代码的 server」，需要在 `models/server`、`models/tunnel`、
  `views/TunnelsView.vue`、`views/PortForwardsView.vue` 四处看注释才能对上。
- 未来若做公开 API 或插件体系，建议一次性把内部名改成 `connection` / `forward`，
  并在那时做一次 DTO 迁移；现在不做。

## 备选方案（未采用）

| 方案 | 为什么没选 |
|---|---|
| 内部名一起改 | 破坏契约、改动面大、纯收益为负 |
| 保持「服务器 / 隧道」 | 与我们想强调的「一条连接上挂多条转发」不符，且用户明确要求改成这套词 |
| 用「会话 / 转发」 | 「隧道」更贴近 SSH 语境 |
