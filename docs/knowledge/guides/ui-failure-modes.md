# 界面上的"失败"必须有声音——三种静默形态与排查法

> 后端返回错误、界面却什么都没说，是最难被用户接受的一类 bug：
> 用户不知道是自己点错了、还是程序坏了、还是网络慢。

本项目在两天内连续踩了两次，形态不同、根因同类。这里把可复用的判定记录下来。

## 三种静默形态

### 1. 按钮被 `disabled`，且没有任何解释

```ts
function canRemove(state) { return state !== 'running'; }
```
```vue
<button :disabled="!canRemove(state)">删除</button>
```

- 表现：点下去毫无反应。没有请求、没有提示、没有 loading。
- 排查：全局搜 `:disabled=`，逐条问"这个条件用户能不能自己改？"
  - **能**（状态类，如"运行中不许删"）→ 这是业务规则，应该**允许操作 + 确认框**，
    或者**禁用 + 可见的原因**（title/说明文字）。只禁用不说话，等于 bug。
  - **不能**（操作进行中、环境不支持）→ 合理，保留。
- 本项目的结论：`busyKey / saving / serviceBusy / refreshPending` 属"进行中"，
  `!isTauri()` 属"环境不支持"，其余一律不该因状态禁用。

### 2. 错误信息被后续的成功调用抹掉

```ts
async function create(req) {
  await guard(() => api.create(req));  // 失败：lastError = "端口已被占用"
  await refresh();                     // 成功：lastError = ''  ← 抹掉了
}
```

- 表现：失败却弹"已添加成功"，列表里也没有。
- 根因：用**一个共享的 `lastError`** 同时表达"列表拉取失败"和"写操作失败"，
  而 `refresh()` 成功时会清空它。两个语义挤在一个变量里，谁后跑谁说了算。
- 规则：
  - **读取类**失败与**写入类**失败不要共用一个槽位；
  - 刷新的成功**不能**清写操作的错误；
  - 动作开始时清空、结束时写入，才不会被中间的成功调用覆盖。
- 更彻底的做法是让方法**返回结果**（`string | null`）而不是依赖共享状态，
  但这需要改所有调用点——本项目先按上面的语义约束修，并加了单测守住。

### 3. 成功提示放在"没检查结果"的路径上

```ts
await doSomething();
ElMessage.success('已完成');   // 没看返回值/错误
```

- 表现：提示成功，但什么都没发生。
- 规则：**先判断结果，再提示**；判断依据是"后端返回"或"列表里确实出现了"，
  不是"代码执行到这一行"。

## 排查清单（改完界面后过一遍）

- [ ] 每个 `:disabled` 都能回答"用户为什么点不了"，且答案是用户可理解的
- [ ] 每个写操作都有失败分支，且失败信息**在提示成功之前**被检查
- [ ] 提示成功的条件来自数据（列表/返回值），而不是"代码跑到了"
- [ ] 连续两次失败/成功后，第二次的提示不携带上一次的结论
- [ ] 破坏性操作（删除运行中的东西、断开连接）有确认框，说清"会发生什么"

## 怎么验证

- 界面自动化点击在本项目环境里不可靠（WebView2 收不到注入的鼠标事件），所以：
  - **逻辑层**用单测覆盖（例：`models/tunnels.test.ts` 里"失败后刷新不能抹掉错误"）；
  - **接口层**用脚本打真实核心（例：`scripts/check-port-conflict.py`、
    `check-delete-running.py`），确认报文与副作用（端口是否释放）；
  - 需要看渲染时，用临时注入复现时序，截图确认后**立刻移除临时代码**。
