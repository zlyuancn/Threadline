# 「没有隧道却有流量」——派生状态里的残留键

> 界面显示的速率不是后端给的，而是前端按两次采样自己算的。凡是这种
> **由列表推导出来的状态**，最容易出的错不是算错数，而是**该消失的项没消失**。

## 现象

侧栏写着「0 条隧道正在运行」，下面却还挂着 `↑ 928 B/s ↓ 198.2 KB/s`。
数字不再跳动，停在隧道停止那一刻，看起来"有东西还在跑"。

## 根因

```ts
// 错法：用上一轮的结果做底板，只覆盖本轮出现的实体
const nextRates = { ...rates.value };
for (const item of items) {
  nextRates[item.id] = computeRate(item);   // 只写"还在的"
}
rates.value = nextRates;
```

- 被删除 / 停止的转发**不会再进入循环**，它的 key 就永远留在表里；
- 合计（`totalSpeed`）无脑遍历整张表，于是把这个不再更新的僵尸值一直加进去；
- 单看某个转发的速率是 0（因为没人再算它），看合计却非 0——**矛盾只在汇总层暴露**，
  逐项检查时反而"一切正常"。

## 规则

1. 派生状态每轮**从空重建**，只装本轮仍在列表里的实体（和 `nextSamples` 一个待遇）。
2. 需要"沿用上一轮值"时，必须**显式写回同一个 key**，不能靠"整体拷贝上一轮"顺手带上。
   两者语义完全不同：
   - 沿用 = 这个实体还在，只是这次没算（间隔太短）；
   - 残留 = 这个实体已经没了，本不该被统计。
3. 汇总函数（`total*`）应当信任上游"表里只有活着的实体"，不要在每个调用点再过滤一遍——
   过滤写散了就有人漏写。

```ts
const nextRates: Record<string, Rate> = {};          // 空表起手
for (const item of items) {
  if (elapsed < MIN_INTERVAL_MS) {
    nextRates[id] = rates.value[id] ?? ZERO;          // 显式沿用
    continue;
  }
  nextRates[id] = computeRate(item);
}
// 本轮没出现的实体：自然不在 nextRates 里，合计立刻归零
```

## 怎么验证

- **逻辑层**：单测两连发——先采样出非零速率，再 `sample([])`，断言 `totalSpeed` 归零。
  这是唯一能稳定复现的路径（等真机手动停隧道靠运气）。见 `src/models/traffic.test.ts`。
- **界面层**：不要只截"有速率"的图。真正要截的是**空列表 + 无速率**那张——
  缺陷只在"项消失"的那一刻显形。
- 反向用例也要有：间隔过短的采样**不能**把数字抹成 0（否则修残留会引入闪烁）。

## 排查清单

- [ ] 派生状态（速率、计数、徽标、汇总）是否都从空表重建？
- [ ] 有没有 `{ ...prev }` 这种"顺手继承"的写法？逐个问：上一轮的 key 凭什么还在？
- [ ] 实体被删除/停止的那一次刷新，是否有断言或截图确认显示归零？
- [ ] 单测里有没有"列表变空"这条用例？只有"有数据"的用例挡不住这类 bug。

## 附带教训：验证用的注入数据要标明、要清掉

为验证"第二行速率会不会挤坏布局"，用 devtools/eval 往 DOM 里插了一对**假速率**，
截图时没标注。结果看图的人第一反应是"0 条隧道哪来的流量"——把假数据当成了 bug 报告。

- 截图给他人看之前，先确认画面里的每个数字都来自真实运行；
- 必须注入时，在截图旁边写明「注入值」或直接注掉再做；
- 反过来也有价值：这次"误读"顺藤摸出了上面那个真 bug——**别急着解释掉异常，
  先按"如果这是真的"去查一遍**。
