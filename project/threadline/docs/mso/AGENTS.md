# MSO 架构 · AI 协作规则

> 本文件给 AI 助手看。在采用/评审「模型自组织架构（MSO）」的代码库中工作时，遵循本文。
> 人看的介绍在 [README.zh-CN.md](README.zh-CN.md)（英文版 [README.md](README.md)）；本文只写可执行的精确规则。English: [AGENTS.md](AGENTS.md)

## 术语（精确定义）

| 术语 | 定义 |
|---|---|
| **模型（Model）** | 最小自闭环单元：**独占**自己的数据 + 自带规则与操作 + 只暴露窄 API。判据：能用一句话说清「我拥有什么数据、提供什么操作」 |
| **聚合（Aggregate Group）** | 相关模型的自然组合；同时是文件组织与代码评审的边界。**不是硬性层级**，允许按实际情况调整归属 |
| **接口层** | 协议适配（HTTP/RPC/CLI/前端视图）。禁止出现业务规则 |
| **业务层** | 用例编排：调度模型完成动作。**禁止拥有规则本体** |
| **模型层** | 数据与规则的所有者。内部自组织：树形组合 + 横向调用 + 允许有终止保障的环 |
| **应用壳（Shell）** | 装配体：把三层装进某个可运行的应用（进程与入口形态，如 Web 服务 / 桌面程序 / CLI）。不含业务规则，越薄越好 |
| **组合根（Composition Root）** | 唯一装配点：负责 port 注入与壳的组装 |
| **port** | 模型/聚合对外的窄接口。横向调用的唯一合法通道 |
| **底座（Foundation）** | 无业务语义的基础设施（存储/配置/日志/工具、终止/预算/重入防护/超时组件）。被上层单向依赖 |
| **业务角色模型** | 回答「某业务域内谁能做什么」（如管理员/成员）。属于某个聚合内的普通模型 |
| **共享模型（Shared Model）** | 被 ≥2 个聚合复用、但**带业务规则**的模型（区别于底座——底座无规则）。同样受三条核心纪律约束 |
| **横切上下文** | 不属于任何模型、但整条链路都要用的公共信息（用户身份、租户、链路追踪号、语言/时区等）。由底座隐式传播、显式读取；无上下文的流程必须显式声明 |

## 硬规则

### 1. 依赖方向（单向，不许反向）

```
应用壳 → ① 接口层 → ② 业务层 → ③ 模型层 → 底座
```

- 模型之间：允许横向调用，但**只走对方 port（公开操作）**
- 底座：**不许** import 任何上层
- 接口层：**不许**出现业务规则
- 跨进程/跨设备的模型实例之间：只走线缆协议，**同进程**才允许组合根注入的 port 直调

### 2. 模型层核心纪律（仅三条；落地时另有流程纪律，见「渐进落地」节）

1. **环允许（A→B→A 合法），但每条环必须有终止保障**：
   - **「每条环」是环级要求，不是节点级**：环上**任一**模型声明终止保障即可，不要求逐节点都声明——否则正常的双向只读询问（A 查 B 的存在性、B 查 A 的引用关系）会被误判为违规。
   - **纯只读 port 可显式声明相位**（`pub const TERMINATION = "phase"`）：只读、无副作用、不推进任何状态，不构成需要终止保障的环。
   - 终止机制分两层：
     - **底座统一提供的组件**：**预算**（调用预算耗尽即停）/ **重入防护**（进行中标记，重入直接返回）/ **超时**。由底座统一实现、统一测试；**模型禁止私有实现**——各写各的私有机制会互相不知情、质量参差、不可审计
     - **模型层设计选项**：**状态机相位**（每相位只许单向推进）——设计约束而非可下沉组件，需在模型契约中声明
   - 每条环必须有证明「会停」的测试
   - 语言约束：Go 包级 import 环是编译错误。模型在包内文件组阶段天然合法；拆独立包时环上模型合并成包，或在环上切刀换接口（组合根装配）
2. **窄 API + 数据独占**：横向调用只走对方公开操作；数据谁拥有谁写，禁止直接读写其他模型的内部状态
3. **业务层不藏规则**：「谁能做X」「什么条件下Y」这类判定必须归属某个模型；业务层只编排

### 3. 粒度是分形的（同一套规则适用于任意尺度）

模型 → 聚合 → 进程/微服务，是同一思想的不同粒度，**三条纪律在每层都成立**：

| 粒度 | 数据独占 | 窄 API | 终止保障 |
|---|---|---|---|
| 模型（包内） | 独占 struct / 数据表 | 方法接口 | 重入防护 / 调用预算 |
| 聚合（文件组） | 独占目录 / 表域 | 组合根注入的 port | 状态机相位 |
| 微服务（进程） | 独占数据库（禁共享库） | HTTP / gRPC / 消息 | 超时 / 重试预算 / 熔断 |

评审跨服务代码时，把「一个微服务」当作一个大模型套用同样的清单：它有没有独占数据？接口窄不窄？跨服务环有没有终止保障？

表格列的是各粒度适用的机制，不是实现方：重入防护与调用预算由底座实现，状态机相位是在模型契约中声明的设计选项。

### 4. 横切上下文的传播

横切上下文：不属于任何模型、但整条链路都要用的公共信息——用户身份、租户、链路追踪号、语言/时区等。

它没有归属模型，既有纪律让它无路可走：存全局变量共享 → 违反「数据独占」；每个方法加参数层层传 → 违反「窄 API」。唯一正路：

1. **隐式传播**：由底座/框架把上下文挂在执行流程上自动向下带，业务代码不经手
2. **显式读取**：模型通过底座提供的统一读取 API 取值，不读全局、不改签名
3. **缺失必须显式**：没有上下文的执行流程（定时任务、批处理、内部触发）必须显式声明「本流程无上下文」，代码必须处理「取不到」分支；**禁止把「取不到」当成「没有限制」继续执行**

场景：请求经 订单 → 库存 → 通知 三个模型。「当前用户」走参数，则三层每个方法都要加 userId；走全局变量，则三模型共写一块状态。正路是框架自动向下带、各模型统一 API 读取。反例：某内部流程取不到「可见范围」上下文，代码把「取不到」当成「不限制」，导出了本不该导出的数据——缺失的上下文被静默当成了默认放行。

### 5. 通知权归属（状态变更与副作用通知同点发出）

模型状态发生变化时，**通知外界的副作用事件（渲染/审计/下游订阅）必须由拥有该状态的模型在同一处发出**——改状态与发通知是同一个动作，不允许拆成两条可独立走的路：

- 任何模型/编排/壳，禁止只改状态不发通知（下游永远看不见），也禁止只发通知不改状态（谎报）
- 同一用例存在多个触发方（真实操作、定时赠送、调试注入）时，必须收敛到**唯一施放入口**——入口内原子完成「生效 + 通知」，新触发方只准调入口，禁止复刻其内部流程
- 状态与通知分离的代码即便行为当前正确，也必然在下一个新触发方出现时产生「状态变了、通知没发」的静默缺陷

场景：弹球落口触发技能——sim 在模型内部同时改状态并 push 事件，渲染层消费事件播特效，行为正确。调试代码绕开 sim 直接改状态 → 事件流为空 → 特效永不出现。正路不是让下游去 diff 状态，而是注入方补发与 sim 同构的合成事件，或收敛到统一施放入口。

### 6. 机检规则（CI 拦截，评审兜底）

纪律只靠人眼评审必然被侵蚀——纸面规定被绕过，往往事故后才被发现。核心纪律的可机检子集必须配静态检查、在 CI 拦截：

| 纪律 | 可机检子集 | 不可机检部分（评审清单兜底） |
|---|---|---|
| 依赖方向 | import 方向静态检查：下层/平级禁止 import 上层与内部文件 | 调用是否语义上越权 |
| 窄 API + 数据独占 | 模型对外接口的签名禁止引用其他模型的内部类型 | 数据写入口是否唯一 |
| 环必须有终止保障 | 环检测 + 环上调用必须命中底座终止组件或已声明的相位机制 | 「会停」测试的业务合理性 |

正例：订单模型只 import 库存模型的公开接口文件 → 检查通过。反例：订单模型 import 了库存模型的内部数据文件 → 提交当场被拦。对比没有检查时：违规埋进代码，三个月后线上出了数据互改事故，才有人翻出那条从没人遵守的规定。

机检是必要条件而非充分条件：拦得住结构违规，拦不住语义越权——后者由评审清单兜底；CI 已拦截的项不再挂评审清单。

**机检本身也要被验证（两个硬要求）**：

1. **自证**：机检 MUST 带 `--selftest`，且自测用例覆盖**已知绕过形态**——至少：注释掉的违规代码、组合导入（`use crate::{a::X, b::Y}`）、模块路径重定向（`#[path]`）、别名与取函数引用（`use ...::f; f()`、`let f = ...::f; f()`）、方法调用与 turbofish 形态、glob 导入。自测 MUST 进门禁（与正式检查同一命令链）。理由：正则写出来的规则几乎总能用一处空白、一个花括号或一行注释绕过去，只有反例用例能证明规则真的拦得住。
2. **声明必须是代码级**：任何被机检采信的语义声明（如"这个环有终止保障""这个 port 只读"）MUST 以代码形式存在（常量、属性、真实函数调用），**注释不算**——注释可以被随手加上，等于没有约束。机检实现 MUST 在匹配前剥离注释，避免注释成为免死金牌。

**壳/组合根的签名级细化**（堵「壳变厚」的结构性漏洞）：组合根确实要 import 一切，依赖方向检查对壳必然放行；但「装配型 import」与「施放/编排型调用」可以用导出命名约定区分并机检——例如壳/接口层禁止 import 模型的工厂/操作导出（`spawn*`/`make*`/`activate*` 等），只允许经业务层暴露的统一入口（如施放入口、编排用例）。前提是唯一施放入口已存在（见 §5）；无入口时先落入口再加禁令，否则机检误伤正常装配。

### 7. 共享模型的准入与去向

底座必须无业务语义，但现实中带规则的能力会从业务模型里长出来。判断时机：**第二个使用方出现时**。

- 能力仍住在第一个模型内部、第二个模型开始需要它 → 不能让后者翻前者内部，必须搬出来
- 搬去哪：**带业务规则** → 固化为共享模型（受三条核心纪律约束）；**纯机制、无规则** → 沉入底座

场景：订单模型里写了一段「满 100 减 20」的优惠计算，退款流程也要算同样的优惠——第二个使用方出现了，这段代码必须搬出订单模型；它含「谁享几折」的规则，去共享模型。若只是个四舍五入工具，不含任何业务规则，去底座。

### 8. 反模式（评审时发现即报）

- **上帝对象**：多个领域的字段与方法共享一个 struct/class，多把锁共用一个宿主
- **全局 god-model**：所有领域共用一个模型包，改一处波及全仓
- **业务层藏规则**：编排代码里出现「判断角色/权限/状态」的规则逻辑
- **模型互翻数据**：直接读改其他模型的内部字段/表
- **无终止保障的环**：A→B→A 且没有任何会停机制
- **私有终止实现**：模型自带预算计数/重试循环而不使用底座组件。反例：多个模型各自实现了无退避的重试，下游一抖动同时开火，重试风暴把下游打挂——底座组件自带退避与熔断，私有轮子一个都没有
- **上下文逐参数透传**：为传横切上下文给每层方法加参数，签名层层污染（正路见「横切上下文的传播」）
- **存量专项大重构**：为「让老代码符合架构」立项专项重构（正路见「渐进落地」补充纪律）
- **壳变厚**：应用壳里长出业务逻辑
- **状态与通知分离**：改状态与发副作用通知不在同一处发出；外部路径（调试注入/补偿任务/旁路工具）只改状态不发通知，下游消费者静默失明（正路见「通知权归属」）
- **为拆而拆**：拆出的模型说不出一句话判据

## 评审清单（写代码 / review 时逐项自查）

- [ ] 新逻辑有归属吗？属于哪个模型？一句话判据能通过吗？通不过 → 先设计归属再动手
- [ ] 判定规则落在模型里了吗？业务层是否只有编排？
- [ ] 跨模型调用走对方公开 API 了吗？有没有直翻内部数据？
- [ ] 新增了环吗？终止机制是什么？有「会停」的测试吗？
- [ ] 接口层是否混入了规则？壳是否变厚了？
- [ ] 是否存在绕过机检的动态依赖（反射、字符串拼包名），破坏依赖方向或进入底座内部实现？
- [ ] 每个模型的文件头契约是否写明：拥有什么数据 / 提供什么操作 / **允许调用谁**（横向调用清单）？
- [ ] 共享模型（被多个聚合复用）是否仍满足数据独占 + 窄 API + 终止保障？
- [ ] 终止保障用的是底座组件（或已声明的相位机制）吗？有没有私有预算/重试实现？
- [ ] 横切上下文走底座隐式传播 + 显式读取了吗？有没有逐参数透传？「取不到」的分支处理了吗？
- [ ] 被第二个使用方需要的能力，走「准入判断」了吗（带规则 → 共享模型；纯机制 → 底座）？
- [ ] 同一用例的新触发方（真实操作/定时赠送/调试注入）走唯一施放入口了吗？有没有绕开入口复刻「生效+通知」流程？
- [ ] 机检装上了吗、在 CI（或本地门禁）拦截吗？壳/接口层有没有施放型调用绕过签名级禁令？

## 渐进落地（存量系统 · 行为零变化，每步全量测试全绿才进下一步）

| 步骤 | 动作 | 边界 |
|---|---|---|
| 0 盘点 | **四透镜**穷举无主物：数据所有权 / 规则不变量 / 生命周期 / 流程用例；产出 100% 文件→模型映射 | 无归属文件进「待定」列并写理由 |
| 1 文档化 | 每个模型写契约（拥有/提供/允许调用清单） | 不改代码结构 |
| 2 包内文件组 | 按模型归组文件、写文件头契约 | 不建新包、不跨包搬文件 |
| 3 提真包 | 文件组提升为独立包 | 环上模型合并成包或切刀换接口；按聚合独立 commit |

补充纪律：
- 基线红了先收口：存量测试失败时先修绿（或记录豁免清单），迁移期间豁免清单只减不增——否则「每步全绿」无从判定
- 拆分粒度防走偏：**先量后拆**——行数/职责数据说话；拆不动的记录理由，不为拆而拆
- 未结构化存量（无分层、大文件平铺）：契约文档先行，代码归组只在需求自然触碰时进行，禁止为「符合架构」立项专项重构
- 大文件重组时测试文件随行；每步跑全量门禁（vet/test/fmt/前端测试）
- 模型清单是活文档：新增模型走四透镜检查，防遗漏

## 采用与溯源

本节即安装流程。项目采用 MSO 时，按顺序执行一次：

1. **落地规则副本**：把与项目语言一致的规则文件（英文项目 `AGENTS.md`、中文项目 `AGENTS.zh-CN.md`）复制为采用项目的 `docs/mso/AGENTS.md`
2. **在根规则文件留引用**：在该项目 AI 规则文件（如其 `AGENTS.md`）顶部记录：

```
架构：模型自组织架构（MSO）
本地副本：docs/mso/AGENTS.md —— 任何涉及架构的设计、写码、评审前先读它；不要重新联网下载
来源：https://github.com/zly-app/mso-arch（规则版本：<commit 或日期>）
```

3. **读本地**：未来 AI 会话读本地副本，不再访问网络。
4. **装机检（同次采用内完成，不得延后）**：按 §6 落机检最小集——import 方向静态检查接入 CI 或本地门禁脚本；有唯一施放入口后追加壳/接口层的施放禁令。规则要求了机检，安装流程就必须交付机检——只装文档不装机检 = 纪律靠人眼，必然被侵蚀。

理由：一个项目会开多个 AI 会话，每次会话都重新联网下载规则既慢又依赖网络。落地副本是随时可用的基准，根规则文件保持精简（三行）。项目会漂移——随着功能迭代与代码重构，模型边界会逐渐被侵蚀，纪律会被零碎突破。本地副本加来源记录让每个未来会话都有固定基准可对照校准，防止架构随时间漂移。

- Mermaid 可表达的用 mermaid（GitHub 原生渲染）
